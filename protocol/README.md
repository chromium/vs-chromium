# VsChromium protocol

The messages exchanged between `VsChromium.Server` and its clients (the Visual Studio extension and
the VS Code extension): **JSON-RPC 2.0** over the standard input/output of the server.

This directory is the **single source of truth** of the protocol. The code of the server and of the
clients is generated from it by [src/Tools/ProtocolGen](../src/Tools/ProtocolGen), on every build
(incrementally: only when a `.tsp` file or the generator changed):

| Output | Generated file | Status |
|---|---|---|
| Server (C#, System.Text.Json source generation, NativeAOT compatible) | [src/Server/Protocol/Generated/Protocol.g.cs](../src/Server/Protocol/Generated/Protocol.g.cs) | Generated |
| Visual Studio extension (C# 7.3, Newtonsoft.Json, StreamJsonRpc) | [src/VsChromium/Protocol/Generated/Protocol.g.cs](../src/VsChromium/Protocol/Generated/Protocol.g.cs) | Generated |
| VS Code extension (TypeScript, vscode-jsonrpc) | [src/vscode/src/protocol/protocol.g.ts](../src/vscode/src/protocol/protocol.g.ts) | Generated |

The three files are regenerated by the build of `src/Server` (`GenerateProtocol` target). To
run the generator by hand:

```
dotnet build src\Tools\ProtocolGen -c Release
dotnet Binaries\Release\Tools\ProtocolGen\VsChromium.ProtocolGen.dll --input protocol --server-cs src\Server\Protocol\Generated\Protocol.g.cs --vs-cs src\VsChromium\Protocol\Generated\Protocol.g.cs --ts src\vscode\src\protocol\protocol.g.ts
```

Contents of the client files:

- **Visual Studio**: the models and enums, `ProtocolMethods` (method names), `ProtocolClient` (one
  `XxxAsync` method per request, wrapping a `StreamJsonRpc.JsonRpc`; parameters are sent as a
  single object) and `IProtocolNotifications` (one method per notification, to implement and
  register with `JsonRpc.AddLocalRpcTarget<IProtocolNotifications>(target, null)`).
- **VS Code**: the models (interfaces) and enums (string literal unions), one namespace per request
  (`SearchCodeRequest.type`, a `RequestType`) and per notification
  (`IndexStateChangedNotification.type`, a `NotificationType`), to use with
  `MessageConnection.sendRequest` and `onNotification`.

The generated code is in the `VsChromium.Protocol.Generated` namespace (`.Generated` is appended to the namespace of the definition files). The generated files are checked in (diffs show the effect of protocol changes). The test
`ProtocolGenTests.RepositoryGeneratedFilesAreUpToDate` fails if a checked-in file is stale.

## Language: a subset of TypeSpec

The files use a subset of [TypeSpec](https://typespec.io), parsed by our own generator (no Node.js
needed to build). They are valid TypeSpec: the official editor extensions ("TypeSpec for Visual
Studio", "TypeSpec for VS Code") give syntax colors, errors and navigation, and the official
compiler accepts them (`tsp compile protocol/main.tsp --no-emit`, checked with TypeSpec 1.0).

Supported:

```typespec
namespace VsChromium.Protocol;          // one file level namespace (the same in all the files)
import "./other.tsp";                   // imports (for the TypeSpec tools; the generator reads all the files)

/** Documentation comments are copied to the generated code. */
model SearchParams {
  query: SearchQuery;                   // model reference
  maxResults: int32;                    // scalars: string, boolean, int32, int64, float64, utcDateTime
  patterns: string[];                   // arrays
  matchCase?: boolean;                  // optional property (omitted from the JSON when not set)
  ...DetailsParams;                     // spread: copies the properties of another model
}

enum IndexingStatus { idle, paused, `yield`, busy }   // serialized as strings ("idle")

interface Search {                      // requests (client -> server): method "search/code"
  code(...SearchParams): SearchCodeResult;            // parameters: the properties of a model
  register(path: string): void;                       // inline parameters, no result
  refresh(): void;                                    // no parameters
}

interface IndexNotifications {          // notifications (server -> client): method "index/stateChanged"
  stateChanged(...IndexStateChangedParams): void;
}
```

Not supported (reported as errors by the generator, with the location): decorators, directives,
templates, inheritance (`extends`, `is`), unions and literal types, aliases, scalars declarations,
anonymous models, default values, namespace blocks, other scalar types.

## Rules

- **Names**: models, enums and interfaces in PascalCase; properties, parameters, operations and enum
  members in camelCase: they are the JSON names.
- **Methods**: `<group>/<operation>`, where the group is the interface name in camelCase. Interfaces
  whose name ends with `Notifications` declare notifications sent by the server (operations
  returning `void`); the group is the name without the suffix (`IndexNotifications` -> `index/...`).
- **Parameters** are always an object (JSON-RPC named parameters): the properties of the spread model,
  or of a model generated from the inline parameters (`<Group><Operation>Params`, e.g.
  `FilesRegisterParams`).
- **Protobuf compatibility** (every message can be expressed in proto3): results are models (not
  scalars or arrays), no optional arrays (use an empty array), no arrays of arrays, no inheritance
  or polymorphism, no maps.
- **JSON**: camelCase properties, enums as strings, `utcDateTime` as RFC 3339 strings, 64 bit integers
  as JSON numbers (the server also accepts strings, as written by the protobuf JSON mapping).

## Transport

Implemented by the server (`src/Server/JsonRpc`): the only protocol of the server since phase P5
(the typed messages protocol, JSON lines, was removed). Used by the VS Code extension (P3) and the
Visual Studio extension (P4).

- **Server argument**: `VsChromium.Server.exe --jsonrpc` (`--stdio` is an alias, the usual LSP
  convention).
  The messages are exchanged over the standard input/output of the server (stdout is reserved for
  the protocol, the console output goes to stderr). **The server exits when its standard input is
  closed** (end of stream).
- **Framing** (as the Language Server Protocol): each message is a list of headers, each terminated
  by `\r\n`, an empty line (`\r\n`), then the content: `Content-Length` bytes of UTF-8 JSON.
  `Content-Length` is required; other headers (e.g. `Content-Type`) are ignored; header names are
  case-insensitive. Invalid headers (or a stream ending in the middle of a message) end the
  connection: the server sends a `-32700` error with a null id and stops reading (exits). A UTF-8
  BOM at the very start of the input is skipped (written by .NET Framework clients).
- **Messages**: JSON-RPC 2.0. `"jsonrpc": "2.0"` is required. Requests (`id` + `method` +
  optional `params`, an object), notifications (no `id`). Ids are numbers or strings, echoed as is in
  the responses. Results are always present in successful responses (`null` for methods returning
  `void`). Batches (arrays) are not supported. Requests without parameters (`index/pause`,
  `index/resume`, `tree/refresh`) accept missing or empty `params`; the others require an object.
- **Concurrency**: requests are processed concurrently, and their responses can be sent in any
  order; `index/pause` and `index/resume` are processed one at a time, in the order they were
  received (the state changes asynchronously after the response: see `index/stateChanged`).
- **Cancellation**: the client sends the notification `$/cancelRequest` with `{ "id": <request id> }`.
  A cancelled request fails with `-32800` (even if it completed in the meantime, unless its response
  was already sent). Unknown ids are ignored. As before, a new code or path search also cancels
  the search running at the same time (`-32800` too).
- **Notifications from the client** other than `$/cancelRequest` are ignored.
- **Errors** (`error: { code, message, data? }`):

  | Code | Meaning |
  |---|---|
  | `-32700` | Parse error: invalid JSON, or invalid framing (null id) |
  | `-32600` | Invalid request: not a JSON object, `jsonrpc` not `"2.0"`, no `method`, `id` or `params` of the wrong type, id already used by a pending request |
  | `-32601` | Unknown method |
  | `-32602` | Invalid parameters (missing, not an object, or not matching the definition) |
  | `-32603` | Internal error (unexpected exception); `data` is an `ErrorInfo` (message, type name, stack trace, inner error) |
  | `-32001` | Expected error, to show to the user as is (`message`): e.g. invalid regular expression, project or directory not found, invalid project path |
  | `-32800` | Request cancelled (LSP `RequestCancelled`) |

Differences with the former typed messages protocol (besides the envelope): flat search results (see
`search/code`, `search/paths`); `tree/entries` and `tree/entriesMultiple` return the names of the
sub directories and files (`DirectoryEntries`, `exists: false` for a missing directory) instead of a
`DirectoryEntry` tree one level deep (or null), and echo the requested relative path; `tree/get`
returns no projects when `knownVersion` is the current version; `server/initialize` replaces the
"hello" message (the server doesn't send anything before the first request); the server records
the duration of each request as `Request:<method>` in the `operationTimings` of
`server/statistics` (was `Request:<request type name>`).
